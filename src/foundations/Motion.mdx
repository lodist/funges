# Motion

Three durations and one easing curve. Every transition in the application
references them; a hardcoded `200ms` is a bug even when the number is right,
because the next retune will not find it. That includes a number that is right
by coincidence: Tailwind's own default transition is 150ms on
`cubic-bezier(0.4, 0, 0.2, 1)`, identical to `--transition-duration-fast` and
`--ease-standard`, and it would not have moved either.

## Durations

Press **Run** to feel each one. Reading `150ms` off a table tells you nothing
about whether it is the right choice.

<Story of={MotionStories.Durations} />

Pick by what is moving, not by taste:

- **`--transition-duration-fast` (150ms)** — a surface reacting under the pointer. Hover
  and press escalation, nothing that travels.
- **`--transition-duration-base` (200ms)** — the default. If you are unsure, this is the
  answer.
- **`--transition-duration-slow` (300ms)** — a large surface covering real distance, like
  a Sheet sliding in from an edge.

## Easing

<Story of={MotionStories.Easing} />

One curve for everything. `cubic-bezier(0.4, 0, 0.2, 1)` accelerates fast and
decelerates gently, so a surface reads as settling rather than snapping.

Adding a second easing token is a design decision, not a convenience — the
value of having one curve is that motion across the app feels like one system.

## In code

The scale is named with Tailwind's `--transition-duration-*` prefix, so it _is_
the `duration-*` utility namespace: write `duration-fast`, `duration-base`,
`duration-slow`, and `ease-standard`. Nothing needs an arbitrary value.

A bare `transition-colors` with no `duration-*` beside it is also correct —
`--default-transition-duration` and `--default-transition-timing-function` are
pointed at `--transition-duration-fast` and `--ease-standard`, so the Tailwind
default is the project default.

framer-motion cannot read a CSS custom property, so the same values exist once
more as numbers in `src/lib/motion.ts` (`DURATION_FAST`, `DURATION_BASE`,
`DURATION_SLOW`, `EASE_STANDARD`). Import from there rather than typing `0.2`;
`src/test/motion.test.ts` fails if the two copies drift apart.

One exception, deliberate: press feedback in `SpeciesSelector` is a spring, and
a spring has no duration to reference. Note that framer-motion **discards**
`duration` whenever `stiffness` or `damping` is set, so writing both does not
document the timing — it hides that the timing is something else entirely.

## Reduced motion

<Story of={MotionStories.ReducedMotion} />

When the viewer asks for reduced motion, animations and transitions collapse to
`0.01ms` rather than being removed. That distinction is deliberate: a
transition that never fires can leave a component wedged mid-state, while one
that completes instantly cannot.

It takes two rules, because the app animates in two ways. The CSS half is a
global `*` rule that shortens every `transition-duration` and
`animation-duration`. The JS half is `<MotionConfig reducedMotion='user'>` in
`__root.tsx`: framer-motion writes inline transforms from JavaScript, which no
CSS rule can reach, and its own default is `reducedMotion: 'never'` — so
without that provider a reduced-motion viewer still got the full animation.

Both are global. Individual components do not need to check the preference
themselves — but a component that animates outside CSS and outside
framer-motion (a Web Animations call, a manual `requestAnimationFrame` loop)
is covered by neither, and has to check.
